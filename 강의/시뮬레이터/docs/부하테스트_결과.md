**현재 설정(폴링 2초 · tick 1초 · 배치 2초)을 유지한다.**

### 2-5. 왜 이렇게 여유가 있나

읽기 API 가 DB 를 조회하지 않기 때문이다.
시뮬레이션 상태는 **API 서버 프로세스 메모리**에 있고, Supabase 로는 배치로 흘려보낸다.
학생 폴링은 메모리 스냅샷을 직렬화해 돌려주는 것뿐이다.

이 설계 덕분에 학생 수가 늘어도 **DB 부하가 늘지 않는다**.
늘어나는 것은 API 서버의 CPU 뿐이고, 그쪽 여유가 크다(마지막 tick 처리 0~15ms).

Supabase 쪽 부하는 학생 수와 무관하게 **네임스페이스 수에만 비례**한다.
39 네임스페이스 = 312행/초 고정이다.

## 3. Supabase 쓰기 부하 · 저장 용량

| 항목 | 실측 |
|---|---|
| 적재 속도 | **312행/초** (설비 234 + 로봇 78) |
| 배치 1회(2초분) | 624행 |
| 배치 적재 소요 | **234 ms** (`copy_records_to_table`, 왕복 포함) |
| `sensor_readings` 행 크기 | 약 158 B (인덱스 포함) |
| `robot_readings` 행 크기 | 약 161 B (인덱스 포함) |
| **시간당 증가량** | **약 180 MB** |

무료 티어 DB 한도가 500MB 이므로 **`RETENTION_HOURS=1`** 을 기본값으로 정했다.
러너가 180초마다 `prune_readings()` 를 호출해 1시간 넘은 이력을 지운다.

측정 중 관찰값: 25분 운전 후 DB 81.8MB (`sensor_readings` 53MB · `robot_readings` 18MB).
1시간 보존 기준 정상 상태는 200~280MB 부근으로 예상된다(autovacuum 재사용 포함).

> Pro 전환 시 DB 8GB 이므로 `RETENTION_HOURS` 를 2~4 로 올려도 된다.
> 다만 하루 4시간 수업이라 1시간으로도 실습에 지장이 없다.
> 학생이 **과거를 훑는 실습(2일차)은 전부 나눠 주는 7일치 CSV** 로 하고,
> 이 DB 에는 **지금 흐르는 값만** 있으면 된다. 그래서 짧게 잡아도 무방하다.

> 보존 시간은 **가상 시각** 기준으로 잰다. 배속 ×120 이면 공장 시계가 실제보다
> 빨리 흐르므로 같은 1시간이 실제로는 30초분밖에 안 남긴다 — 배속 구간에서
> 이력이 갑자기 짧아 보이는 것은 고장이 아니다.

## 5. 이상 주입 3종 실측 (완료기준 ③)

| 이상 | 조건 | 실측 |
|---|---|---|
| 온도 드리프트 | 0.5℃/h · 4시간 (유일한 기준값) | 62.59 → 64.55℃ · 고정 임계값 80℃ 미도달 · TEMP_HIGH 미발생 |

| 센서 결측 | 120초(가상) | `temperature`/`vibration`/`rpm` 전부 `null` 적재 · 30초 후 **SENSOR_LOSS** 발생 · 종료 후 복귀 |

**드리프트가 고정 임계값을 넘지 않는 것은 의도한 것이다.**
2일차 슬라이드 서사("80도를 넘은 적이 없다")와 2일차 미탐 학습의 전제다.
그래서 드리프트 파라미터는 **기준값 하나뿐**이고, 라이브 시연은 기울기가 아니라
배속으로 만든다(6절). 알람이 필요한 시연에는 진동 스파이크나 센서 결측을 쓴다.

한편 설비별 정상 온도가 서로 다르게 설계돼 있어(EQ-04 56℃ ~ EQ-05 75℃),
슬라이드의 *"선을 66도로 낮추면 다른 설비들이 하루 종일 울린다"* 가
시뮬레이터 안에서 실제로 성립한다.

## 5-1. 가상 시계 — 라이브 시연이 서사·알고리즘과 어긋나지 않는가

라이브 시연에서 4시간짜리 드리프트를 보여줄 때 **기울기를 키우지 않고 시계를 가속**한다.
기울기를 키우면 샘플당 상승폭이 커져 두 가지가 동시에 깨지기 때문이다.

- 2일차 논지 — *"한 시간에 0.5도는 눈으로 구분되지 않는다"*
- 2일차 학습 — *"드리프트는 이동평균이 적응해 미탐된다"* (z-score 가 쉽게 잡으면 3일차 시연과 모순)

### 불변식 실측 — 실제 적재 데이터 회귀분석

배속 ×60 으로 서사 기준값(0.5℃/h · 4시간)을 주입하고, Supabase 에 적재된
`sensor_readings` 를 램프 구간만 잘라 최소제곱 회귀했다.

| 항목 | 실측 | 기대 |
|---|---|---|
| 램프 구간 샘플 수 | **241개** | 가상 4시간 ÷ 1분 = 240 + 시작점 1 |
| 가상 샘플 간격 | **60초** | 7일치 CSV 격자와 동일 |
| 회귀 기울기 | **0.5012 ± 0.0379 ℃/시간** | 0.5 (주입값) |
| **샘플당 상승폭** | **0.008353 ℃/샘플** | **0.008333** (CSV: 0.5℃/h × 1분) |
| 구간 총 상승 | **2.00 ℃** | 2.0 (62 → 64℃) |
| 잔차 표준편차 | 0.348 ℃ | 0.35 (설정 노이즈) |
| 최고 온도 | **64.55 ℃** | 80℃ 미도달 |

**샘플당 상승폭이 CSV 와 같으므로 이상감지 알고리즘 검증 결과가 그대로 유효하다.**
2일차에서 "드리프트는 미탐된다"를 가르치고 3일차에서 같은 데이터로 시연해도 모순이 없다.

### 배속별 성질 (엔진 자체 검증 항목)

| 배속 | 실제 tick | 가상 step | 샘플당 상승폭 | 공장 4시간 | 총 상승 |
|---|---|---|---|---|---|
| ×1 | 1.00초 | 1초 | — | 4시간 | — |
| **×60** | **1.00초** | 60초 | 0.008333℃ | **4분** | 2.000℃ |
| ×80 | 0.75초 | 60초 | 0.008333℃ | 3분 | 2.000℃ |
| ×120 | 0.50초 | 60초 | 0.008333℃ | 2분 | 2.000℃ |

**×60 에서는 실제 tick 이 정확히 1초**라 교안 3절의 「1초 주기 변동」이 문자 그대로 유지되고
적재량도 ×1 과 같다(312행/초).

### 부수 검증

| 항목 | 결과 |
|---|---|
| 가속해도 고정 임계값 80℃ 미도달 · TEMP_HIGH 미발생 | 최고 64.62℃ ✔ |
| 3초짜리 스파이크가 가상 샘플 한 칸으로 보정돼 데이터에 잡힘 | 2.46 → 10.55 mm/s ✔ |
| AMR 주행은 배속과 무관하게 실시간 | 9틱(실제 9초) 이동, ETA 9.9초 ✔ |

AMR 주행만 실제 시간을 따르는 것은 의도한 예외다. 가상 시간으로 움직이면 ×60 에서
공장을 가로지르는 데 0.2초가 걸려 눈에 안 보이는데, 3일차 클라이맥스가
「화면에서 AMR 이 실제로 움직인다」이기 때문이다.

## 7. 부수 검증

### 7-1. 엔진 자체 검증 (`tools/selftest_engine.py`)

DB 없이 도는 48개 항목 전부 통과(측정 당시 — 이후 주입 만료 회귀검사가 추가돼 현재는 53개). 가상 시계 불변식 검증을 포함한다.
강의장에서 네트워크가 막혔을 때 "시뮬레이터 자체는 정상"임을 즉시 가릴 수 있다.

### 7-2. 권한 (`tools/check_grants.py`)

**제작 중 실제로 뚫렸던 두 가지를 막고 재검증했다.**

| 구멍 | 실측 | 조치 후 |
|---|---|---|
| publishable(anon) 키로 남의 알람 INSERT | `201 Created` | `401 permission denied` |
| 뷰(`equipment_latest`)를 통한 남의 설비 UPDATE — RLS 를 걸어도 통과 | `204`, `run_state` 실제 변경됨 | `401 permission denied for view` |
| `tenant.access_key` 공개 노출 | 읽힘 | `401` (읽기용 `tenant_public` 뷰로 분리) |

원인은 두 가지였다.
① Supabase 가 public 스키마 새 테이블에 anon 쓰기 권한까지 기본 부여한다.
② PostgreSQL 15+ 뷰는 기본이 소유자 권한 실행(`security_invoker=false`)이고
   단순 뷰는 자동 갱신 가능이라, 테이블 RLS 를 뷰가 우회한다.

`db/always/900_grants.sql` 에서 **RLS 가 아니라 권한 회수**로 막았다.
리서치의 "RLS 비채택" 결정(정책 부담·Realtime 처리량 저하)을 유지하면서 같은 목적을 달성한다.

### 7-3. 재기동 내성

- 재기동 전 남아 있던 OPEN 알람 자동 정리됨 ✔
  (엔진 상태는 메모리라 재기동 시 공장이 정상으로 초기화되는데, DB 알람이 남으면
  존재하지 않는 이상이 학생 화면에 영원히 떠 있게 된다 — 제작 중 실제로 재현되어 수정)
- 재기동 시 이전 이상 주입 자동 비활성화 ✔
  (공장이 정상 상태로 초기화되므로 주입만 복원하면 경과 4시간이 반영돼 온도가 +2℃ 튄다.
  가상 시계도 실제 시각으로 되돌아가 기준이 어긋난다. 강사가 다시 주입하는 편이 예측 가능하다)

### 7-4. 폴백 경로

`tools/fallback/state_updater.py` 로 API 서버·2D 뷰 없이 상태만 갱신하고,
`web/fallback/index.html` 이 Supabase PostgREST 를 직접 폴링해 표를 갱신하는 것을 확인했다.
설비 6행 · 로봇 2행 · 알람이 모두 표시됐다.

## 3. 실서버 40명 전 과정 실측 (2026-08-19 · GCP VM)

1절의 단서(무료 티어·단일 PC)를 해소했다 — **실제 운영 VM**(e2-small · 34.64.94.16)에
**강사+39명이 같은 순간에** 수업 전 과정을 진행했다. 판정은 평균이 아니라 **개인별 장부**다.

| 단계 (동시) | 결과 |
|---|---|
| 강사+39명 배정 | 40명 전원 · 중복 0 |
| 배속 ×120 + 전체 드리프트 주입 | 폴링 40명 위에서 정상 |
| 39명 센서+정비 조회 | 39/39 · 전원 WO-2026-0801 |
| **39명 AI 진단 (실제 OpenAI 중계)** | **39/39 · 전체 12초** — 동시 12 관문이 줄 세워 처리 |
| 39명 감속+로봇 파견 | 전원 접수 · 39곳 전수 대조 교차 오염 0 · 남의 키 거부 |
| 6분 지속 폴링 (40명 · 2초 간격) | 화면 7,314장 · **개인별 실패 0 · 뒤처짐 0** · p95 19ms · 최대 235ms |
| 원상복구 | 배정 0 · 주입 0 |

**여유 탐사** — 폴링 인원을 늘려도: 80명 p95 20ms · 160명 p95 22ms · 240명 p95 23ms, 실패 0.
**수업(40명)의 6배까지 여유**가 있어 VM 증설은 불필요하다.

**배정 동시성** — 깨끗한 상태에서 3라운드: 39/39 · 중복 0 · 재실행 유지 39/39.
단, **유령 배정이 1건이라도 남아 있으면 마지막 학생이 「자리 없음」을 본다** (실측 재현)
→ 2일차 진행.md 아침 점검 4번(배정 0 확인)으로 방어.

**몰림 방어 로직 (코드 감사)** — 진단 중계: 테넌트당 분당 12회(429) · 전역 동시 12
세마포어(OpenAI 로는 12개씩만 나가고 나머지는 서버 안에서 줄을 선다) · 429/503 지수 백오프
4회 재시도 · 실패 시 학생 쪽 `rules` 대체. 배정 장부: 원자적 쓰기(tmp→rename)+깨짐 복구.
프로세스: `Restart=always`.

**키 순환의 한계 (정확히)** — OpenAI 의 RPM/TPM 은 **키가 아니라 조직·프로젝트 단위**다.
같은 조직 키를 여러 개 돌려도 처리량은 안 는다. 순환의 실효는 **페일오버**(한 키가
죽어도 예비 키로 수업 지속)뿐이고, 한도 분산은 다른 조직 키일 때만 유효하다.
지금은 키 1개 — 실측상 관문+백오프만으로 39명 동시가 12초에 소화되므로 충분하다.
처리량을 정말 늘려야 하면 키 추가가 아니라 **usage tier 승급**이 맞는 길이다.
잘못된 요청(스키마 불량)은 즉시 503 으로 반려됨을 실측으로 확인 — 조용히 물고 있지 않는다.
