# §1. Lab 3-1 — 레거시 센서 데이터 적재 (30분)

### 왜 하는가 (교안 원문)

> 피지컬 AI의 첫 관문은 모델이 아니라 데이터다. 현장 CSV를 DB에 넣는 일이
> 실무의 절반이다.

현장 데이터의 90%는 실시간 스트림이 아니라 **레거시**(오래된 기록)입니다. 오늘 받는
CSV가 바로 그것 — K-정밀 공장의 **지난 7일치 기록**입니다. 이걸 DB에 넣어야
"지난주에 무슨 일이 있었나"를 물을 수 있게 됩니다.

### 1-1. CSV 받기 (3분)

`[■ 배포 — CSV 배포 경로 확정 후 기입 (실습 저장소 포함 예정)]`

받는 파일: **7일치 센서 기록 CSV, 60,480행** (기계 6대 × 7일 × 1분 간격).
컬럼 6개는 어제부터 여러분 DB에 쌓이고 있는 실시간 데이터와 **완전히 같습니다**:

`equipment_id · timestamp · temperature · vibration · rpm · run_state`

> 이 7일치 안에 **이상 상황 3군데가 심어져 있습니다.** 어디인지는 아직 비밀입니다 —

Claude에게 이렇게 시킵니다 (그대로 붙여넣고 파일 경로만 확인):

넣었다고 믿지 말고 확인합니다. Claude에게:

③ 설비별 행 수를 조회하는 쿼리를 만들어 실행해 줘.

**성공 판정 세 가지:**

# §2. Lab 3-2 — 이상감지 알고리즘 직접 구현 (50분)

### 왜 하는가 (교안 원문)

> **이 랩만큼은 AI에게 통째로 맡기지 않는다.** 전공에서 배운 알고리즘 감각이
> AI 시대에 왜 여전히 무기인지 확인하는 시간이다.

3일 내내 AI에게 시켰는데 왜 이것만 직접 짤까요 — 마지막 단계(Step 3)에서 AI가 짠
것과 나란히 놓고 **판정하는 쪽**에 서 보기 위해서입니다. 판정할 수 있는 사람만이
AI를 도구로 부릴 수 있습니다.

### 2-1. Step 1 — TODO 세 군데 채우기 (25분)

실습 저장소의 `Lab3-2_이상감지뼈대/` 폴더를 엽니다. **`detect.py` 한 파일만 건드립니다.**

만드는 것: **이동 윈도 z-score 이상감지** — "최근 W개 값의 평균에서 지금 값이
표준편차의 몇 배(z-score)나 벗어났나"로 이상을 판정하는 고전적이고 강력한 방법입니다.

| TODO | 함수 | 채울 내용 |
|---|---|---|
| 1 | `window_stats()` | 직전 W개 값으로 평균·표준편차 계산 |
| 2 | `is_anomaly()` | z-score 가 임계값 k 를 넘는지 판정 |
| 3 | `handle_missing()` | 값이 안 들어온 자리(결측)를 어떻게 다룰지 — **정답이 여러 개인 문제** |

- C만 하다 온 사람을 위한 **인덱싱·슬라이싱 힌트 박스**가 파일 안에 붙어 있습니다.
  (예: 직전 W개는 `values[i-w:i]`)
- **15분이 지나면 강사가 첫 번째 힌트 카드를 전체 공개**합니다. 막혀 있는 게
  정상 범위라는 뜻이니 부담 갖지 마세요.

### 2-2. Step 2 — 7일치에 돌려보기 (15분)

```bash
python run.py              # 내 구현을 7일치 데이터에 돌린다
```

**여기서 오늘의 첫 반전이 나옵니다. 예상 결과:**

| 심어진 이상 | 내 코드가 잡나 |
|---|---|
| 진동 스파이크 (순간 급증) | **잡힙니다** — 3건 모두. z-score가 즉시 반응 |
| 센서 결측 (2시간 먹통) | TODO 3을 어떻게 짰냐에 따라 갈림 |
| 온도 드리프트 (서서히 상승) | **못 잡습니다** — 누구의 구현이든 |

드리프트가 안 잡히는 건 여러분 잘못이 아니라 **z-score의 구조적 한계**입니다:
값이 천천히 오르면 "최근 평균"도 같이 올라서, 벗어남이 계산되지 않습니다.
**이 한계를 기억해 두세요 — 내일 팀 챌린지가 정확히 이 문제에서 시작합니다.**

이제 임계값을 흔들어 봅니다:

```bash
python run.py --k 2.0      # 더 민감하게
python run.py --window 30  # 윈도를 짧게
```

**두 번째 반전:** k를 낮추면 드리프트가 잡힐 것 같지만 — 잡히기 전에 **멀쩡한 구간의
오탐(엉뚱한 경보)이 20배로 폭증**합니다. "민감하게 하면 다 잡히겠지"가 왜 현장에서
통하지 않는지, 오탐↔미탐의 맞바꿈을 여기서 몸으로 확인합니다.

`[■ 캡처 — run.py 실행 결과 화면: 스파이크 3건 검출 표시]`

# §3. Lab 3-3 — 내 코드를 MCP 도구로 + 진단 에이전트 (70분)

### 왜 하는가 (교안 원문)

> 알고리즘이 혼자 돌면 스크립트, 에이전트가 도구로 쓰면 지능이 된다.

방금 짠 `detect()`는 아직 스크립트입니다. 이걸 **MCP 도구**로 내놓으면, AI가
"지난주 이상 점검해 줘"라는 말을 듣고 **알아서 여러분의 코드를 호출**하게 됩니다.
MCP(Model Context Protocol)는 AI에게 외부 프로그램을 '손'으로 달아주는 표준 규약입니다 —
오늘은 '읽는 손', 내일은 '움직이는 손'입니다.

### 3-0. 준비 (5분)

```bash
cd Lab3-3_MCP도구템플릿
pip install -r requirements.txt
```

`config.json` 을 열어 `student_db` 에 **내 Supabase 접속 정보**(Day 2 것)를 넣습니다.

> **Day 2를 못 끝냈다면:** `config.json` 의 `data_source` 를 `"fallback"` 으로 바꾸세요.
> 센서값은 받아둔 CSV에서, 정비 이력은 강사 쪽 공용 데이터에서 오도록 이미 만들어져
> 있습니다. **어느 쪽이든 도구 이름과 응답 형태는 같아서, 이후 단계는 동일하게 진행됩니다.**

### 3-1. Step 1 — 도구 2개 완성하기 (25분)

`mcp_server.py` 의 ★ **두 자리**를 채웁니다. 이번엔 Lab 3-2와 달리 **Claude와 함께
해도 됩니다** — 알고리즘은 이미 여러분이 짰고, 지금 하는 건 연결이니까요.

| 도구 | 무엇 | 핵심 |
|---|---|---|
| `detect_anomaly` | Lab 3-2에서 내가 짠 `detect()` 를 에이전트가 부를 수 있게 | 내 코드를 그대로 불러 씀 |
| `query_equipment` | 설비 조회 — 최근 센서 요약 + **정비 이력** | 정비 이력의 `note` 가 진단의 실마리 |

서버 뼈대·전송·데이터 가져오기는 이미 완성돼 있습니다. **도구 본문만** 채우면 됩니다.

**중간 점검** (서버 없이 도구만 실행):

```bash
python mcp_server.py --check
```

**성공 판정** — 두 도구의 응답 JSON이 출력됩니다. `query_equipment` 응답 안에
`WO-2026-0801 … 부품 입고 지연으로 보류` 같은 정비 기록이 보이면 완벽합니다.
(이 기록이 잠시 뒤 에이전트가 찾아낼 **원인의 실마리**입니다.)

> ⚠️ Claude가 `mcp.server.fastmcp` 를 쓰라고 하면 거절하세요 — 그건 구버전(1.x) 문법입니다.
> 템플릿의 `from mcp.server import MCPServer` 를 그대로 둡니다 (SDK 2.x 고정).

### 3-2. Step 2 — 에이전트에게 말로 지시 (30분)

서버를 켜고, Claude 플러그인에 내 MCP 서버를 등록합니다:

```bash
python mcp_server.py       # 켜 둔 채로 둡니다
```

`[■ MCP등록 — 플러그인에 서버를 등록하는 정확한 절차·캡처. D-7 리허설에서 플러그인
버전 기준으로 확정]`

등록됐으면, 에이전트에게 **오늘의 지시문**을 내립니다:

```
지난 주 설비 이상을 점검하고, 이상이 있으면 해당 설비의 정비 이력을 조회해
원인 추정과 권고 조치를 담은 진단 리포트를 작성하라.
```

**이제 지켜보세요.** 에이전트가 여러분이 만든 도구를 **줄줄이 이어서** 호출합니다 —
`detect_anomaly` 로 6대를 점검하고 → 이상이 나온 설비에 `query_equipment` 를 다시
호출하고 → 정비 기록의 "부품 입고 지연으로 보류"를 찾아내 → 원인 추정과 권고 조치가
담긴 리포트를 써냅니다.

**성공 판정** — 리포트에 ① 이상 설비 지목 ② 원인 추정 ③ **정비 기록 번호
(WO-2026-…) 인용** ④ 권고 조치, 네 가지가 들어 있으면 성공.
**여러분이 짠 코드가 방금 AI의 손이 되었습니다.** 이게 오늘의 '와' 순간입니다.

`[■ 캡처 — 에이전트가 도구를 연쇄 호출하는 화면 + 완성된 진단 리포트]`

### 3-3. Step 3 — 3일치를 한 화면에 (15분)

그 진단 리포트를 **Day 1에 만든 내 대시보드**에 표시합니다. Claude에게:

```
내 대시보드에 "진단 리포트" 패널을 추가해 줘. 방금 만든 진단 리포트 내용을
거기 표시해 줘.
```

**성공 판정** — 한 화면에: 공장 실시간 상태(Day 1) + 그 공장의 이상 진단(오늘)이
같이 보입니다. **3일치 작업이 합쳐진 화면**입니다.

단 — 에이전트는 아직 **'제안'만** 합니다. 리포트가 "속도를 낮추라"고 권고해도
공장은 그대로 돕니다. **움직이는 건 내일입니다.**
