W1

완료 · 부하검증 조건부

검증됨 — 돌려서 확인한 것

  • 39 네임스페이스 × 8행/초 = 312행/초 적재, tick 누락 0
  • 제어 API 4종 전부 동작 + 감사 로그 기록
  • 이상 3종 주입 — 드리프트·스파이크·결측
  • 네임스페이스 분리 — 8개 동시 제어, 교차 오염 0건
  • 폐루프 성립 — 감속 시 온도 실제 하강 (1800rpm 61.6℃ → 900rpm 46.4℃)
  • 가상 시계 — 배속 ×60에서 샘플당 상승폭이 W5와 동일(0.008353 vs 0.008333℃), 회귀 기울기 0.5012±0.038℃/h
  • 공개 키 권한 — 읽기만 가능, 쓰기 전면 차단
  • 폴백 경로 — API 서버·2D 뷰 없이 Supabase만으로 동작
  • 엔진 자체검증 48항목 통과 (DB 없이)
  • 권한 자동 복구 — 구멍을 일부러 내고 migrate.py up 만으로 복구되는 것 확인
  • Day 1 시연 화면 — 덱B 33장 「볼 것 셋」이 1920×1080에서 스크롤 없이 한 화면

미완 — 조건이 갖춰져야 가능

  • 39명 부하검증(완료기준 ④) — 지금 수치는 무료 티어 + 부하 발생기가 서버와 같은 PC. 검증된 것은 “39 네임스페이스 규모에서 기능이 도는가”까지
  • Pro 전환 후 재측정 (D-14)
  • 강의장에서 다른 단말로 재측정 (D-7) — 무선 구간이 들어가야 의미가 있다
  • 강의장 방화벽이 Supabase 5432 아웃바운드를 막는지 확인
  • 실제 브라우저 39대 동시 렌더 확인 (HTTP 부하와 별개)
  • 자격증명 교체 — 제작 중 오간 DB 비밀번호·시크릿 키
  • Day 4 팀 전환 리허설 (TENANT_MODE=team)
제작 중 실제로 뚫려서 고친 것
  • publishable(anon) 키로 남의 알람 INSERT가 됐다 (201 Created) — Supabase가 public 스키마 새 테이블에 anon 쓰기 권한까지 기본 부여
  • RLS를 걸어도 뷰를 통해 남의 설비 UPDATE가 통과했다 — PostgreSQL 15+ 뷰는 기본이 소유자 권한 실행이고 단순 뷰는 자동 갱신 가능
  • 재기동 후 존재하지 않는 알람이 학생 화면에 영원히 남았다 — 엔진은 메모리라 초기화되는데 DB 알람은 남음

사람 기억에 맡기지 않도록 러너에 묶었습니다. ALTER DEFAULT PRIVILEGES는 새 테이블의 쓰기 권한을 자동으로 막지만 뷰의 security_invoker는 자동화되지 않는 것을 실측으로 확인했습니다. 그래서 db/always/900_grants.sql을 두고 migrate.py up이 매번 마지막에 다시 적용 + 검증합니다. 구멍을 일부러 내고 up만으로 복구되는 것까지 확인했습니다.

교안에 없어 판단한 것 1건 — 확인 바랍니다

감지 기준을 z-score에서 「창 밖 비교」로 바꿨습니다. Day 3에서 증명한 대로 이동창 z-score는 드리프트를 못 잡습니다 — 창까지 같이 올라가기 때문입니다. 같은 데이터로 실측하면 드리프트 2건 vs 평탄 2건으로 구분 자체가 안 됩니다. Day 4 시연이 “드리프트 주입 → 감지”로 시작하므로 감지 기준이 달라야 시연이 성립합니다.

교안 1~3장이 “어제 만든 에이전트 부검”이라 이 대비를 그 자리에 놓았습니다. 강의자료 쪽에서 부검 슬라이드에 이 수치를 쓰실 수 있습니다.

제작 중 실제로 터졌다가 고친 것 — 검증이 놓쳤던 결함

실습 중반부터 드리프트가 안 잡히는 상태였습니다. 감지가 “최근 12분”을 통째로 보는데, 루프를 오래 돌릴수록 창이 길어지고 드리프트는 그 안의 짧은 구간이라 앞뒤 평균 차이가 희석됩니다. 실측하니 12분치가 쌓인 뒤에는 차이가 +0.50℃로 주저앉아 임계(0.8℃)를 못 넘었습니다.

검증이 이걸 못 잡은 이유가 더 중요합니다. 매 검증이 reset 직후에 돌아서 창에 2~3분치밖에 없었습니다. 즉 가장 유리한 조건만 재고 있었습니다. 8팀 부하를 재다가 요청당 1,440행이 오는 것을 보고 발견했습니다.

조치 — 최근 600샘플(가상 10시간) 상한을 두고 임계를 0.4℃로 내렸습니다(오탐 최대 0.08℃, 5배 여유). 정상 상태 90~230초, 갓 켠 팀 40초부터 검출. 검증에 “오래 돌린 상태” 항목 3개를 추가했고, 상한을 빼면 실제로 실패하는 것까지 확인했습니다.

4일치 무인 리허설 — 이제 “통과했다”가 무슨 뜻인지 알 수 있습니다

리허설_4일치.py 를 만들었습니다. Day 1 부터 Day 4 까지 한 번도 초기화하지 않고 연속으로 돌리며, 학생이 무언가 하는 시점마다 학생이 보는 것을 검사합니다. 규칙은 하나 — 시작할 때 한 번 말고는 초기화 금지. 제작 중 두 번 놓친 결함이 전부 “짧게 돌면 통과·오래 돌면 실패”였기 때문입니다.

돌리자마자 실제 결함이 하나 더 나왔습니다. 진단 모델이 “+0.4℃면 심각도 LOW” 라며 조치를 하나도 내지 않아 폐루프가 안 닫혔습니다. 감지는 드리프트를 일찍 잡으려 작은 값에서 울리는데, 그 숫자만 보여 주니 모델이 “아직 별것 아니다”로 판단한 것입니다. 지시문에 “드리프트는 지금 작아도 계속 오른다”를 넣어 고쳤고, 같은 조건 10회 재시험에서 10/10 조치를 냅니다. Day 1 에서 사람이 놓친 이유와 같은 함정이라 학생 힌트에도 적어 뒀습니다.

현재 39항목 전 통과 · 총 8분 33초 (Day1 14 · Day2 3 · Day3 6 · Day4 16). 검사하지 않은 항목은 “건너뜀”으로 따로 셉니다 — 침묵이 성공처럼 보이지 않게 했습니다. D-7 강의장에서 그대로 돌리면 “이 방에서 4일이 돌아간다”가 증명됩니다.

강사가 기억할 것을 없앴습니다 — 교안에 없는 조작이라 교안이 안 알려줍니다
  • 배속을 기본값으로 박았습니다(×60). 강사가 켤 스위치가 아닙니다. ×60은 실제 tick이 정확히 1.00초라 교안 3절의 “1초에 한 번씩 바뀐다”가 문자 그대로 유지되고, 적재량도 ×1과 같으며, 샘플 간격이 가상 1분이 되어 부록 A 레거시 CSV(1분 격자)와 격자가 일치합니다
  • 팀 공간을 처음부터 띄웁니다(47개). Day 4에 팀 모드로 바꾸려고 서버를 재시작할 일이 없습니다
  • Day 4 준비는 명령 하나 — python tools/day4.py (제어 개방 + 배속 + 팀별 키 출력). 발표 때는 --inject T3
  • 콘솔이 빠뜨린 것을 스스로 말합니다 — 제어를 열었는데 배속이 1이거나 주입이 없으면 경고. 학생 쪽 loop.py --check도 같은 것을 경고합니다
  • 주입 응답이 실제 소요 시간을 알려줍니다 — 지속시간이 가상 시간 기준이라 배속이 걸리면 빨리 끝나는 함정이 있었습니다

실측 — 기본값만으로 47 네임스페이스 369행/초·tick지연 0, 최악 조건(×120·39명 폴링)에서도 에러 0 · p95 84ms. 주입 → 감지는 ×60에서 79~190초.

데모 발표 3분 — 운영 방식이 필요합니다

팀이 loop.py를 켜 둔 상태로 발표하고, 직전 팀 발표 중에 강사가 --inject 하는 순서를 발표 안내에 넣어 주십시오. 감지에 79~190초가 걸려, 발표석에서 처음 켜면 시연 3분이 대기로 갑니다.

부수 산출 — 동작 보장 최소 경로 카드

0.붙는가 → 1.감지 → 2.진단 → 3.조치 → 4.닫혔는가, 각 단계의 우회 사다리와 강사만 할 수 있는 조치를 분리했습니다. 시간이 없는 팀을 위한 가장 짧은 to_commands()(감속 하나)도 넣었습니다.
