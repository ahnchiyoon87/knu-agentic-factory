# §1. Lab 2-1 — 빈칸 채우기: 관제 스펙 완성 (30분)

### 왜 하는가 (교안 원문)

> AI가 코드를 짜는 시대에 엔지니어의 부가가치는 **'정확한 요구 정의와 검증'** 으로
> 이동한다. 스펙을 읽고 판정하는 근육을 먼저 만든다.

### 1-1. 스펙 문서 열기 (2분)

내 저장소(첫날 만든 것)의 **`2일차/스펙_K정밀_설비관제.md`** 를 VS Code 로 엽니다.

제목은 **"K-정밀 설비관제 시스템"**. 기능 덩어리(capability) 3개로 되어 있습니다:

| capability | 내용 |
|---|---|
| 설비·로봇 마스터 | 공장의 기계·로봇 기본 정보 관리 |
| 알람 규칙 | 임계값 · 등급 · 에스컬레이션(단계적 확대) |
| 정비 작업지시 | 발행 → 수행 → 완료로 이어지는 상태 흐름 |

이 문서는 **일부러 미완성**입니다:
- **빈칸 6군데** — GWT의 Then(그러면 ~해야 한다) 조건이 빠져 있음
- **일부러 틀린 곳 3군데** — Then이 잘못 적혀 있음 (예: "온도 80℃ 초과 시 알람 **해제**")

> **GWT(Given-When-Then)** 복습 — 오전 강의에서 배운 형식입니다:
> Given(이런 상태에서) When(이런 일이 일어나면) Then(시스템은 이렇게 해야 한다).
> "확인 가능한 요구사항"을 쓰는 표준 문형입니다.

### 1-2. 혼자 작업 (20분)

규칙은 세 가지입니다 (오전 강의 15–16장):

1. **빈칸은 채운다** — Then에 들어갈 조건을 스스로 정해 쓴다
2. **적혀 있는 것은 판정한다** — 맞으면 O, 틀리면 X 표시하고 고쳐 쓴다
3. **근거를 쓴다** — 왜 그렇게 채웠/판정했는지 한 줄씩

> **정답은 오늘 오후까지 안 알려줍니다.** 여러분이 틀리게 채우면 §3에서 **그 스펙으로
> 만들어진 시스템이 실제로 틀리게 동작**해서 스스로 드러납니다. 그게 오늘의 설계입니다 —
> 지금은 소신껏 채우세요.

### 1-3. 짝 검토 (10분)

옆 사람과 문서를 바꿔 봅니다. 서로 다르게 채운 곳을 찾아 **왜 다르게 판단했는지**만
이야기하세요. 합의하지 않아도 됩니다 — 누가 맞았는지는 §3가 판정해 줍니다.

# §2. Lab 2-2 — Supabase 온보딩 (30분)

**Supabase**는 클라우드 데이터베이스 서비스입니다 — 여러분의 관제 시스템이 알람·작업지시
데이터를 저장할 곳입니다. 오늘 만드는 계정과 프로젝트는 **내일(데이터 적재)과 모레(진단
에이전트)에도 계속 씁니다.** DB를 처음 쓰는 사람 기준으로 안내합니다.

1. **회원가입** — supabase.com 접속 → GitHub 계정으로 가입 (어제 로그인한 그 계정)
   `[■ 캡처 — 가입 화면]`
2. **프로젝트 생성** — New Project → 이름은 자유(예: `knu-factory`) → 리전은 Seoul →
   **데이터베이스 비밀번호는 만들고 꼭 메모** (다시 안 보여줍니다)
   `[■ 캡처 — 프로젝트 생성 화면]`
3. **SQL 에디터에서 테이블 하나를 손으로** — 왼쪽 메뉴 SQL Editor → 아래를 붙여넣고 Run:

```sql
create table hello_factory (
  id serial primary key,
  name text,
  created_at timestamptz default now()
);
insert into hello_factory (name) values ('첫 테이블');
```

4. **대시보드에서 확인** — 왼쪽 메뉴 Table Editor → `hello_factory` 에 방금 행이
   보이면 성공. `[■ 캡처 — Table Editor 확인 화면]`

**성공 판정** — 4번까지 끝났으면 "DB를 만들고, 표를 만들고, 데이터를 넣고, 눈으로
확인"을 전부 해 본 것입니다. 오늘 오후 AI가 이걸 대신해 줄 때, **뭘 하는지 아는 상태**로
지켜볼 수 있습니다.

**안 되면:**

| 증상 | 조치 |
|---|---|
| 가입이 막힘 (rate limit 류 문구) | 강의장 같은 IP에서 대량 가입 시 걸리는 정책 — 손 들기 (강사가 우회 안내) |
| SQL 에러 | 문구 복사 → Claude에게 (어제의 만능 열쇠) |
| 비밀번호를 메모 안 하고 넘어감 | Settings → Database 에서 Reset password |

# §3. Lab 2-3 — 스펙 → 구현 → 검증 (90분)

여기가 오늘의 본론입니다. §1에서 완성한 스펙이 **진짜 시스템이 되고**, 여러분의
빈칸 판정이 **맞았는지 시스템이 알려주는** 시간입니다.

### 3-1. Step 1 — 스펙에서 시스템 생성 (30분)

완성한 스펙 문서를 통째로 Claude에 넣고 지시합니다:

```
이 스펙 문서대로 Supabase에 테이블 스키마를 만들고, 알람 규칙과 작업지시를
처리하는 API와 간단한 관리 화면을 만들어 줘. 내 Supabase 접속 정보는 (프로젝트
설정에서 복사한 URL과 키). 그리고 어제 만든 내 대시보드에 알람 표시를 연결해 줘.
마지막으로, 공장 API(/{내번호}/readings)에서 센서 값을 주기적으로 받아
sensor_readings 테이블에 쌓는 것도 추가해 줘.
```

AI가 만드는 동안 (수 분) — **로그를 읽으세요.** 지금 테이블을 만드는지, API를 짜는지,
어디서 헤매는지가 다 보입니다. 어제는 결과만 봤다면, 오늘은 **과정을 감독하는 눈**을
연습합니다.

**성공 판정** — ① Supabase Table Editor에 스펙의 테이블들이 생겼다 ② 어제 대시보드에
알람 영역이 붙었다 ③ `sensor_readings` 에 행이 쌓이기 시작했다 (**이게 내일 쓸 재료를
미리 모으는 것입니다** — 내일 아침이면 하룻밤치 데이터가 모여 있습니다).

### 3-2. Step 2 — GWT 검증, 그리고 '대조 해결' (30분)

이제 스펙의 GWT 항목을 **하나씩 실행하며** 체크리스트로 검증합니다. 중간에 강사가
시뮬레이터 콘솔에서 **온도 이벤트를 쏴 줍니다** — 여러분 시스템에 알람이 제대로 뜨는지
보세요.

**여기서 오늘의 진실의 순간이 옵니다:** §1에서 빈칸을 틀리게 채웠거나 틀린 항목을
"맞다"고 판정한 사람은, **여기서 시스템 버그로 만납니다.** (80℃ 초과에 알람이
'해제'되는 시스템이 실제로 만들어져 있을 겁니다.)

그러면: **스펙을 고치고 → 다시 생성.** 코드를 직접 고치지 않습니다 — 문서를 고치면
시스템이 따라옵니다. 이 순환("대조 해결")이 스펙 주도 개발의 핵심 동작입니다.

### 3-3. Step 3 — 어제의 복수전 (30분)

강사가 요구사항 카드를 **딱 1장** 더 던집니다 — 어제 여러분을 무너뜨렸던 바로 그
**"알람 담당자 배정"** 입니다. `[■ 카드]`

이번엔 프롬프트로 처리하지 않습니다. **스펙 문서에 이 요구를 추가**하고 → 다시
생성합니다.

**성공 판정** — 담당자 배정이 붙고, **어제 잘 되던 기능이 하나도 안 깨졌으면** 성공.
어제 3~4장째에서 무너졌던 것과 직접 비교되는, Day 2의 '와' 순간입니다.

- 지원자 2명이 **어제 것과 오늘 것을 나란히** 시연합니다 — 같은 요구, 다른 운명.
- 커밋으로 자산화: **"스펙 저장소가 곧 포트폴리오"** 입니다.

```
git add .
git commit -m "Day2: 스펙 주도 관제 백엔드"
git push
```

- 오늘 가져가는 것 세 줄:
  1. 무너짐의 원인은 AI가 아니라 **요구가 문서화되지 않은 것**이었다
  2. 스펙이 틀리면 시스템이 틀리게 나온다 — **판정 근육**이 그래서 필요하다
  3. `sensor_readings` 에 데이터가 쌓이기 시작했다 — **내일 그걸로 이상을 찾는다**

> 내일 예고: "공장을 보고, 설계했습니다. 내일은 공장의 이상을 **'아는'** 지능을 답니다."
